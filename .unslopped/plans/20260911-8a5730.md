# Require a review artifact on this repository so a cycle cannot release without one

Cycle: 20260911-8a5730
Started: 2026-09-11T15:00:59.087Z

## Goal
This repository has shipped seven cycles with no code review. `reviewArtifact` is false, so the release
gate never asked for one, `reviewCommand` is null, so no second agent ever ran, and every review artifact
on disk was written by the assistant about code it had just written. The project built to stop
assistants certifying their own work has been certifying its own.

Turning the gate on does not make a review independent. It makes it impossible to ship without one, which
is the hole that let seven cycles through.

## Approach
Rung 1. The practice exists, the check exists, the artifact format exists. Nothing needs building. Set
`practices.reviewArtifact` to true in this repository's config.

`reviewArtifactCheck` then demands three things at release: a review is on record, it carries no critical
findings, and its timestamp is newer than the last commit. That third condition is the one that changes
how a cycle runs here. Reviewing before the final commit no longer counts, so the order becomes commit
everything, then review, then release. This cycle proves it by living through it.

A test asserts this repository keeps the practice on, next to the check that asserts it carries its own
CI workflow. Without that, the setting is one careless edit from silently going back to false, and the
evidence for that risk is the seven cycles that just happened.

Independence still comes from two other places, and this cycle changes neither:
- The CI workflow reviews every pull request in a clean environment. It has never run because the GitHub
  Actions account is billing-locked, which is outside this repository.
- `reviewCommand` would run a second agent over the diff before the author sees it. It needs an API key
  and a budget, which is the human's decision, not a cycle's.

Rejected:
- Turning on `reviewApproval` in the same change. It forces a human sign-off on every review, and with
  CI review landing on each pull request that is the same findings approved twice.
- Setting `reviewCommand` here. A cost and a credential decision that belongs to the human.
- Claiming this delivers independent review. It delivers a gate. Saying otherwise would be the exact
  failure this cycle exists to fix.

Revisable: whether `reviewApproval` should follow once CI review is actually running.

## Handoff
What to verify: a cycle in this repository can no longer reach deploy without a review.

How to reach it:
1. Start a cycle, make a change, commit it.
2. Run `unslopped next` at release. It fails with `review artifact: no review recorded`.
3. Record one: `unslopped review --file=<findings.md>`, or let a second agent write the findings.
4. Run `unslopped next` again. It passes.

Rejections to try, with what should happen:
- Record the review, then make another commit, then release: refused, because the review is older than
  the latest commit. Review again after the last commit.
- Record a review carrying a `[critical]` line: refused until the finding is fixed, committed and
  reviewed again.
- Set `practices.reviewArtifact` back to false: the test suite fails, and the config change blocks the
  cycle until a human approves it.

Gotchas:
- This makes a review compulsory, not independent. The assistant writing findings about its own diff is
  what the last seven cycles did, and the gate cannot tell the difference. Real independence needs the CI
  workflow running or a `reviewCommand` configured.
- The order of a cycle changed here: commit everything first, then review, then release. A review
  recorded before the final commit no longer counts.

## Monitor
Ten gate runs for an eleven-line diff, because the gate this cycle turned on applied to the cycle that
turned it on. That was the point, and it was worth watching.

- The release gate refused three times, each time correctly. First with no review recorded. Then with a
  review that had gone stale, because a one-word changelog fix added a commit after it. Then on a dirty
  tree, because the review artifact itself was uncommitted.
- The staleness rule is sharper than it looks. Any commit invalidates the review, including a typo fix,
  so the real order is: finish everything, then review, then release. Front-loading the review wastes it.
- `lastCommitMs` excludes `.unslopped/`, so committing the review artifact does not invalidate the review
  it contains. Without that exclusion the gate would be unsatisfiable, and it is the kind of detail that
  only shows up when the gate is switched on.
- The style gate caught a filler word in the changelog sentence describing this change, which is twice
  now that writing about a rule has broken the rule.
- The finding worth acting on is not this setting. Seven cycles ran before anyone asked whether the
  review gate was on, and nothing anywhere lists which practices are off. A project can carry a disabled
  gate forever without it appearing in `status`, `resume` or any report.

For next time: review last, after the final commit, and treat any later commit as a reason to review
again rather than an inconvenience.
