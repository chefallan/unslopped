# Approvals prompt in the harness by default

Cycle: 20260902-d767ec

## Goal
On hooked assistants, an approval becomes one click instead of a typed command. The assistant runs the approve command, the hook answers "ask", and the harness shows the human a native allow-or-deny prompt carrying the evidence: the proposal text for commit and pr, the brief for deploy. Prompt is the default; a config switch restores the typed ceremony; reset and rollback prompt too, at the user decision, with their consequences spelled out in the prompt body; command mode restores typed ceremony for everything.

## Approach
Chosen: extend the hook verdict with ask. Under the default approvals setting ("prompt"), an approve command at command position returns ask, and the reason carries the evidence read from the cycle: proposal text, deploy brief, or drift note for config. The Claude tool hook emits the permissionDecision JSON with exit 0 for ask and keeps stderr plus exit 2 for denials; the Cursor hook sets permission to ask. With approvals set to "command", denial behavior is unchanged. reset and rollback deny in both modes because a reflex click must never destroy a cycle. The protocol states that an assistant whose platform shows no permission prompts is not hooked and must not run approve.
Rejected: a one-time code the human relays, because the assistant sees everything the terminal prints, so the code proves nothing. Rejected: native OS dialogs spawned by the CLI, because the harness prompt is a trust boundary that already exists and cannot be clicked by the assistant.

## Out of scope
- STE writing rules (separate decision, parked)
- Prompting for reset or rollback
- Any change for unhooked assistants beyond the protocol wording
