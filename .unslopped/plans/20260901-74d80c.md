# Flag exploitable lines during code review

Cycle: 20260901-74d80c

## Goal
Code review points at lines that look exploitable and says in one plain sentence how an attacker would abuse them. The findings ride the existing review pipeline: inline comments on PR reviews, prepended entries in the local review artifact, advisory severity so a heuristic never blocks a merge by itself.

## Approach
Chosen: a curated pattern table in a new src/vulns.ts, scanned over the added lines only, covering the low-false-positive classics: eval and code-from-strings, shell commands built from variables, SQL built by concatenation, HTML sinks, unsafe deserialization, weak password hashing, guessable randomness for secrets, disabled certificate checks, file paths and redirects built from request data. Every hit is a major finding whose text is the plain-words exploit story. Wired where the secret scan already sits: prepended to PR reviews and to the local review artifact, behind practices.exploitScan, on by default. The protocol asks reviewer agents to say how a change could be exploited so their findings match.
Rejected: critical severity or a blocking gate, because these are heuristics and a false positive must never freeze a release; a human or reviewer can escalate a real one. Rejected: shelling out to an external scanner, because unslopped promises zero runtime dependencies and practices.securityScan already covers projects that install one. Rejected: taint tracking, because pretending regexes follow data flow produces confident nonsense.

## Out of scope
- Dependency vulnerabilities (practices.audit already runs npm audit at the build gate)
- A blocking gate for exploit patterns
- Custom user-defined patterns in the config (debt if wanted later)
