# Adapt i-have-adhd: give the assistant a report contract and cap the grouped lists unslopped prints

Cycle: 20260910-9c2581
Started: 2026-09-10T09:23:13.980Z

## Goal
Adapt i-have-adhd (github.com/ayghri/i-have-adhd), ten rules for how an assistant should talk to a
human: lead with the next action, number multi-step work, end on one concrete next step, no preamble, no
recap, no closers, rank and group long lists at five per group, state numbers rather than vague amounts,
be matter-of-fact about failures, make progress visible.

Two gaps here. The protocol spends nine sections on how to work and one line on how to report, so the
report is the least specified thing an assistant does. And unslopped's own debt listing prints every row
in every category with no cap, which is the exact shape rule nine exists to stop.

## Approach
Rung 2 for both halves.

- The report contract goes in protocol.ts, the same place the ladder went. That file generates AGENTS.md,
  CLAUDE.md and every other instruction file, so a rule written once reaches every project and every
  assistant. The existing one-line reporting rule becomes a section with the contract in it.
- The list cap reuses what the other listings already do. `resume` slices its checks to four and the
  bloat scan caps at twelve, so `cmdDebt` gets the same treatment: five rows per category, then a line
  counting what was left out. The grouping already exists; only the slice is new.

No gate checks the report, and the plan says so plainly rather than implying otherwise. Unslopped never
sees the assistant's chat output, so a report contract is a prompt-level rule like the ladder's rungs,
and the only mechanical part of this cycle is the output unslopped produces itself.

Six of the ten rules are already satisfied and get no new text. Restating state every turn is the prompt
hook, which already injects the cycle, the phase and the gate on every message. Ending on a next step is
what `next`, `check` and `resume` already print. Numbers instead of vague amounts is what the gates
already do with exit codes and milliseconds. Matter-of-fact failures is already a rule. Naming them as
absorbed rather than adding duplicate text is rung 1.

Rejected:
- A gate that checks the assistant's report. Unslopped cannot read chat output, so the check would have
  nothing to run on, and a gate that cannot fail is worse than no gate.
- Rewriting every listing in the codebase to a five-item cap. `resume`, the review artifact and the
  impact section are each already capped at a number chosen for what they carry. Changing them to five
  for consistency would cost information for no reader's benefit.
- The time-estimate rule. Estimating how long a human's next step takes means guessing, and every other
  number this tool prints is measured.

Revisable: five rows per category, and whether the contract belongs in its own section or inside Rules.

## Handoff
What to verify: the instructions now say how to report, and the debt listing stops growing.

How to reach it:
1. Open AGENTS.md or CLAUDE.md and read `## How to report`. Eight rules and the source credit.
2. Log six items in one category, then run `unslopped debt`. Five rows, then `1 more, see
   .unslopped/DEBT.md`.
3. Run it with four items in a category. All four, no count line.

Rejections to try, with what should happen:
- A category with nothing in it: absent from the listing, not printed as an empty heading.
- Two categories both over five: each capped on its own, each with its own count line.

Gotchas:
- No gate checks the report. Unslopped never sees the assistant's chat output, so the contract works the
  way the ladder's rungs work, by being in front of the assistant on every prompt. The only mechanical
  part of this cycle is the debt cap.
- The style gate caught a filler word in the contract text itself, which is the tool holding its own
  instructions to the rule they state.
- Version 0.1.8. PR #3 claims 0.1.6 and PR #4 claims 0.1.7, so three open branches each insert a section
  under the same changelog heading. Whichever merges second and third resolves one hunk there and in
  package.json.

## Monitor
One gate failure, and it was the best moment of the cycle: the style gate rejected the word "just" in
the report contract itself. A rule about writing plainly, caught by the check that enforces writing
plainly, before it reached a single reader. That is the tool working on its own instructions.

- Six of the ten source rules were already satisfied. Reading each one against what the tool does before
  writing anything cut the work by more than half. The temptation with a rules list is to adopt all ten
  as text and call it absorbed, which would have added six paragraphs of duplication and made the
  instruction file worse.
- One rule was refused rather than adopted. Time estimates mean guessing, and every other number this
  tool prints is measured. Adopting it would have put the one unverifiable number in a report whose whole
  point is that its numbers are real.
- Three cycles are now open as pull requests at 0.1.6, 0.1.7 and 0.1.8, each inserting a changelog
  section under the same heading. Every one after the first merge has one conflict hunk. Stacking four
  cycles in a day without merging is the cause, and it is a queue problem rather than a code problem.
- The review's third finding is the honest limit of this cycle: nothing verifies the contract, so its
  value rests on an assistant following instructions it can ignore with no gate noticing. That is true of
  the ladder's rungs too. Prompt-level rules are the tool's weakest kind of lever, and worth using only
  where a mechanical check is genuinely impossible.

For next time: read a rules list against what already exists before writing any of it down, and merge
the queue before starting a fifth cycle.
