# Require human approval of commit and PR text

Cycle: 20260901-8c3c78

## Goal
No commit message or pull request text written by an assistant executes without the human reading and approving it first. The assistant proposes, the human approves, the tool executes exactly the approved text, verified by hash. Tracker status comments stay automatic because they are mechanical pings, not authored prose.

## Approach
Chosen: a propose-approve-execute triple. `propose commit` writes the full message to .unslopped/proposals/commit.md and stops. `approve commit` (human-only, hook-blocked like every approval) stores the text hash on the cycle and prints what was approved. `commit` runs git with the proposal file only when the stored hash matches the file, consumes the approval, and refuses when the text changed after approval. `pr` writes its generated title and body to proposals/pr.md and refuses to post until `approve pr`; the hash covers the recomputed text, so any new commit or plan change invalidates the approval by itself. The tool hook denies raw assistant `git commit` while practices.messageApproval is on, which is what makes the flow mandatory rather than polite.
Rejected: approving per-line or editing proposals through the tool, because the human's editor is the right place to change text; they edit the proposal file and approve again. Rejected: gating tracker comments, because approving twenty "moved to release" pings is friction without safety. Rejected: an interactive prompt in the terminal, because assistants run non-interactively; a file plus a named human command fits how every other approval works.

## Out of scope
- Tracker status comments
- PR review comment posting (`review --pr` keeps `--no-post` as its manual path)
- Editing proposals through the CLI
