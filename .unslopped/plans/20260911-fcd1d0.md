# Add a draft posting mode where the assistant writes tracker and pull request text for the human to post

Cycle: 20260911-fcd1d0
Started: 2026-09-11T13:10:02.337Z

## Goal
A mode where the assistant never posts to the tracker or the code host. It writes the text, the human
posts it.

Today the tool is inconsistent with its own philosophy. Commit text needs approval, pull request text
needs approval, the deploy needs approval. Tracker comments and status transitions fire on every phase
change with no approval at all, and they are the one action in the loop that other people see.

## Approach
Rung 2. `.unslopped/proposals/` and the `--no-post` flag already exist. Draft mode routes the three
posting paths through what is there rather than adding a mechanism.

A top-level `posting` key, `"auto"` or `"draft"`, sitting beside `approvals` because it is the same kind
of setting: who performs the outward action. Three paths change when it is `"draft"`:

- `notifyTracker` appends the comment it would have posted, and the status it would have moved to, to
  `.unslopped/proposals/tracker.md`, then prints the path. No API call.
- `openPullRequest` stops after writing `.unslopped/proposals/pr.md`. It still pushes the branch, prints
  the compare URL and the file, and creates nothing.
- `reviewPullRequest` behaves as though `--no-post` were passed, so findings land in a file.

Pushing the branch stays. Draft mode is about not writing on shared surfaces other people read, not
about refusing to move code. Without a push there is no way for the human to open the pull request at
all, so refusing it would break the thing the mode is meant to enable.

Default stays `"auto"` for everyone else. Posting only happens when a tracker credential is configured,
and configuring that credential is the consent. Flipping the default would silently stop tracker updates
for projects that deliberately set one up, which is a regression they did not ask for. `"draft"` is one
line, documented next to the setting it changes.

Rejected:
- A per-command flag instead of a mode. `pr --no-post` already exists and is not enough: the tracker
  posts from `next`, where there is no flag a human would think to pass.
- Defaulting to draft. Consistent with the philosophy, and it would break working integrations on
  upgrade for no request from their owners.
- Refusing the branch push in draft mode. Leaves the human unable to open the pull request the mode
  exists to hand them.
- Separate settings for the tracker and the code host. Two knobs for one decision, and the spec that
  prompted this treats them as one rule.

Revisable: the default, and whether the tracker draft file should be per cycle rather than one growing
file.

## Handoff
What to verify: with draft posting on, nothing the assistant does reaches a place other people read.

How to reach it:
1. Set `"posting": "draft"` at the top level of unslopped.config.json, beside `approvals`.
2. Start a cycle on a repository with a linked issue and a tracker credential. Read
   `.unslopped/proposals/tracker.md`. It holds the comment and the status the cycle would have moved to.
   The issue itself is untouched.
3. Run `unslopped next` a few times. Each phase change appends another entry to the same file.
4. Reach deploy and run `unslopped pr`. The branch pushes, `.unslopped/proposals/pr.md` holds the title
   and body, and no pull request exists.
5. Run `unslopped review --pr=<n> --file=<findings.md>`. The findings print and none are posted.

Rejections to try, with what should happen:
- `"posting": "sometimes"`: treated as `auto`, never as draft. A typo must not silently stop posting.
- Leaving `posting` out entirely: auto, so an existing project keeps its integration on upgrade.
- Draft mode with no tracker credential: the draft file is still written, because drafting does not need
  an API key.

Gotchas:
- The branch is still pushed in draft mode. That is deliberate: without it there is nothing for the
  human to open a pull request from.
- In draft mode `unslopped pr` does not wait for `approve pr`. The approval exists so a human reads the
  text before it goes out, and in this mode the human is the one sending it, so the gate would be asking
  them to approve their own message.
- `.unslopped/proposals/tracker.md` grows across the cycle rather than being written per cycle. Fine for
  one cycle at a time, worth revisiting if that changes.

## Monitor
One gate failure, the scope check again, and this time it was real rather than formatting: `notifyTracker`
needed a `root` to write the draft file, which meant touching `cli.ts` at four call sites and widening
`proposalPath` in `state.ts`. Neither was in the plan because neither was visible until the signature
changed.

- That is the scope check doing its job rather than a mistake to avoid. A function that writes a file now
  needs to know where the repository is, and the plan was written before that was obvious. Declaring the
  two files with the reason took a minute; guessing them in advance would have been guessing.
- The interesting decision was not the mode, it was what draft mode does **not** stop. Pushing the branch
  stays, because refusing it leaves the human unable to open the pull request the mode exists to hand
  them. A rule applied without that exception would have been consistent and useless.
- Draft mode also skips `approve pr`, which took a second look. The approval exists so a human reads the
  text before it goes out; in draft mode the human is the one sending it, so the gate would ask them to
  approve their own message. Keeping it would have been ceremony pretending to be safety.
- The default is the part most likely to be wrong later. `auto` keeps working integrations working, and
  the argument for it is that configuring a tracker credential is the consent to post. If that turns out
  to be too generous, the flip is one line and a changelog note.
- Four review findings, all minor, one logged: `pr status` reports no pull request in draft mode because
  `cycle.pr` is never set when the human opens it by hand. That is the seam where this mode is thinnest.

For next time: when a function starts writing files, expect its callers to join the plan.
